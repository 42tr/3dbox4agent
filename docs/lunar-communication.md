# 月面失联执行与状态恢复

全局“数据流”页的“失联执行与状态恢复”从当前快照读取三类独立依据：中断期间完成的设备动作、明确的通信解除事件，以及解除之后采集并收到的状态报告。任务链完成不充当通信恢复证明。单体视图不读取或显示全局恢复摘要。

动作按完成时刻统计，只计设置中断之后的仿真步，直到中断截止步。与中断设置同一步、但在其之前完成的动作不计入。自动执行模式中的任务不一定对应显式设备动作，因此没有完成记录也不能说明设备没有执行。已接受的意图可以由世界继续推进；独立设备进程也可依据自己的观察提交后续动作。

状态缓存仅保留每台设备最近一份报告。报告必须在本次解除后采集，并在下一次中断前收到，才能作为这一时段的恢复依据；后一次中断的报告不会填补前一次的证据。摘要不把当前缓存称为首次回执，也不从缺失缓存推断从未恢复。报告过期、设备当前已退出、当前未启用状态上报均单独说明。历史恢复依据不等于设备此刻可用或网络连续在线。

投影最多保留最近20次中断，界面显示其中最近10次并标明总数。只读取事件与动作的标识、类型和仿真时刻，不显示自由文本日志、消息正文或凭据；读取不会改变世界或版本。

## 独立进程示例

启动已编译原生后端的本机服务后运行：

```sh
python3 sdk/python/multi_agent_demo.py --url http://127.0.0.1:8787 \
  --schedule-plan examples/experiments/lunar-radio-outage.json \
  --sensor-mode rapier --dispatch networked_reported --link-profile long \
  --clock step --timeout 180 --archive > lunar-radio-outage-run.json
```

将生成的JSON导入页面，在全局“数据流”查看摘要及所选历史快照。步骤时钟会等待进程提交必要决策，这个示例不提供实时吞吐或浏览器帧率结论。完整历史需单独启用持久日志；原始内存报告如被截断会保留原标记。

实际15设备+1指挥进程、种子42、12步延迟和0.1丢包率的记录中，中继2于T50失联时已接受部署任务；T57完成移动并提交后续作业，T65完成作业，T131解除中断。首份恢复后采集的报告采集于T140、收到于T152，完整任务链在T507完成11/11。最终快照只保留更晚的T180/T192回执；它已过期，设备后来因基础耗电退出，因此摘要仍提示当前不可用。

把同一计划的中断持续步数改为1000，另一运行仍在T507完成11/11，却没有解除事件或恢复后报告。这两份实际持久日志各544帧均通过回放校验；原始内存档案保持部分历史，不拼接补造。结果是单一种子下的执行与观测示例，不是算法优劣或所有网络条件的保证。

持续200步的第三份记录在T251解除中断，但中继已先耗尽电量，未收到恢复后采集的报告。界面将这种情形显示为“已解除 · 回执未证实”，同时保留设备当前退出的提示；仅有解除事件仍不足以证明状态通道恢复。

本模型的任务指令和状态报告使用抽象中央链路，延迟、丢包及设备中断会影响它们；设备间显式中继消息另行计算距离、遮挡及逐跳传输。中央任务登记和本机SDK请求不受这条模拟链路阻断，未实现独立确认协议、完整分布式状态合并或中央节点故障模型。
