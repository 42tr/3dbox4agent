# 月面设备协同救援

场景 `lunar-rescue-v1`（[JSON 示例](../examples/scenes/lunar-rescue.json)）沿用月面基地的采样、材料、热控、建设和中继任务。15 台设备完成 11 项任务，其中两台中继车分别部署后留在通信站位。可在首批中继任务启动后注入一次设备故障，由作业机器人现场恢复中继车，重新分配后继续部署。

这是允许现场机械复位的抽象故障模型。它不恢复目标电量，不包含拖曳、零电量供电、换电、氧气、真实维修机构或水面救援。可在“设备故障”面板明确选择空闲、正在执行动作或已驻留的设备。未配置可复位能力的设备故障后仍不能现场恢复。

## 配置与动作

地面设备可配置 `recoverableFault: true`。救援设备必须为地面设备，并同时具备 `rescue` 能力和 `rescue: {"workTicks": 6}` 可复用工具配置；作业时间允许 1–100 步。未配置这些字段的原有场景保持原有行为。

设备通过原有单体动作接口提交：

```json
{"requestId":"reset-1","type":"rescue","targetAgentId":"relay-2","observedTick":12,"faultGeneration":1,"targetTick":13,"expiresTick":53}
```

`observedTick` 和 `faultGeneration` 必须同时对应本机保留的该设备故障观测；后者区分同一步内的多次故障。不能填写全局世界中的未观测设备。世界从已有 `device_fault` 事件绑定内部 `faultSeq`，客户端不能指定该序号。原请求重试返回原动作；即使目标随后再次故障，原请求也不会恢复新故障。

到期时以及每一步作业都会检查目标故障、设备状态和物理范围：距离不超过 4 米，地面通行线无建筑、封路或不可通行坡面阻挡。感知模式可使用实际 Rust 射线。目标电量须大于 5%。同一故障只允许一台救援设备作业，竞争请求不消耗作业电量。

每个实际作业步消耗救援设备的 `workEnergyPerTick`，热保护时暂停进度。取消、故障变化或救援设备耗电退出不会恢复目标，也不返还已经消耗的电量；重新开始需要完成一次完整的作业。完成时保留目标位置、电量、温度和部署身份，并记录唯一 `rescue_completed` 事件。原任务已在故障时撤回，恢复后的设备按新的任务分配代次继续执行。

## 指定设备故障

管理员可调用 `POST /sessions/:id/fault`，请求体为 `{"agentId":"relay-1","expectedFaultGeneration":0}`。可复位设备必须携带当前显示的故障代次；缺失或格式错误返回 400，代次已变化返回 409 且不推进版本。未配置可复位能力的设备须省略该字段。设备、指挥和只读凭据无此权限。原请求体 `{}` 保持首项活动任务故障行为。

故障会终止该设备的待执行与执行中动作；活动任务释放占用、掉落实际携带物并重新排队。空闲和已驻留设备不产生虚假的任务重规划。驻留中继在故障期间停止转发，恢复后保留原站位、部署身份与已消耗材料；此前失败的消息不被重新投递，须使用新的消息 ID。旧故障代次在恢复后仍然失效，不能重试制造第二次故障。

## 查看和运行

网页的“场景与世界设置”中选择“月面设备协同救援”。在“设备操作”中选择有救援工具的机器人，面板仅列出该机器人自己的故障观测。可填入救援接近点并提交移动意图，到达范围后提交现场救援意图；动作记录显示作业进度和终态。历史快照、导入回放和只读观察均不可发出动作。

Python HTTP 与 gRPC SDK 都提供 `rescue(request_id, target_agent_id, observed_tick, target_tick, expires_tick, fault_generation)`。可选的 `task_agent.py --auto-rescue` 策略只读取本机观测，接近目标并提交相同的移动、取消和救援动作，不调用全局世界接口。

```sh
PYTHONPATH=sdk/python python3 sdk/python/multi_agent_demo.py \
  --url http://127.0.0.1:18791 --scene-file examples/scenes/lunar-rescue.json \
  --physics rapier --sensor-mode rapier --dispatch external \
  --fault resident --auto-rescue --clock step --max-ticks 1200 --timeout 180 --archive
```

自动救援仅针对设备自身观测过的故障。默认不探索未知区域；可另行启用下述巡查。默认场景中，首个驻留故障可能处于全部空闲救援机器人的感知范围外，此时即使任务完成，实验也会如实报告未恢复。可通过场景配置调整感知范围，或先给机器人安排巡查/移动任务。

`--fault resident` 在中继真正部署后注入指定设备故障，并检查同一故障事件是否完成现场恢复；即使任务全部完成，未恢复该故障仍报告实验失败。

`--fault recoverable` 仅在当前首项活动任务的设备允许机械复位时，调用已有故障接口。救援策略使用至少 10 步的提前量，为独立进程的异步动作传输留出时间。实验仍需检查完成标志、动作终态和故障记录，不能将提交成功视为恢复成功。

## 验证范围

验证覆盖 JS 与 Rust 每步世界状态一致、六种运动/导航组合的完整月面任务、两种感知模式下的真实 HTTP/gRPC/二进制观测、同故障互斥、取消、再次故障、旧意图失效、正在作业的分支隔离，以及实际提交后异常的全组件/碰撞回滚。回放检查配置、故障代次、作业时长和恢复事件的一致性；这些检查不提供档案来源的真实性认证。

独立 15 设备进程和 1 指挥进程的真实服务联调已完成救援及 11 项任务。第 295 版最终完整回归、最新源码下的独立联调以及浏览器视觉验收记录保存在 `.3dbox/validation/rescue-codex-20261104/`；以对应回执为准。救援控件的浏览器流程仍待预览页面可见后补做，不作为已通过项目。

第 296 版补充指定设备故障、驻留中继与救援机器人连续故障、首次操作的跨世界组件拒绝、实际提交后的回滚、权限与故障代次校验。对应记录位于 `.3dbox/validation/fleet-fault-codex-20261104/`，以实际终态回执为准。


## 可选巡查救援

`task_agent.py` 与 `multi_agent_demo.py` 支持 `--auto-rescue --rescue-search`，两个参数必须一起使用。网页“独立设备进程”在具备救援工具的设备上显示“启用巡查救援”开关，默认关闭；改变草稿会清除旧启动命令，下一次签发时才生成带策略参数的新命令，不改变正在运行的进程。

巡查只读取该设备的有限观察、任务、动作和电量。空闲时在协议定义的0–100米地图内提交普通移动意图，路线、地形和碰撞仍由世界校验。每个进程最多尝试32次巡查移动；目的地不可达时跳过并短暂等待。巡查收到任务、发现本机故障接触或低于电量留量时取消；不会取消操作员或其他进程的动作。留量取20与预计返程能量加5的较大值，并封顶79。取消不退还已消耗能量。

巡查不会生成故障证据。只有获得本机保留的故障观测后，才提交绑定观测时刻与故障代次的原救援动作。实际救援仍受物理距离、工具、电量、热控和互斥约束。巡查不保证发现所有故障，不涉及拖曳、供电或未知区域建图。

```sh
PYTHONPATH=sdk/python python3 sdk/python/multi_agent_demo.py \
  --url http://127.0.0.1:18791 --scene-file examples/scenes/lunar-rescue.json \
  --physics rapier --sensor-mode rapier --dispatch external \
  --fault resident --auto-rescue --rescue-search --clock step --max-ticks 1200 --timeout 180 --archive
```

报告仅在显式启用时包含 `config.rescueSearch: true`。与无巡查的默认25米感知运行比较时，保持场景与种子不变。
